# VERIFIED DEFECTS

1. **CRITICAL — Raen #30 is not actually closed under Raen's threat model.**  
   **Path:** `server.ts:1555–1582` → `/api/notion/write-consent`; `server.ts:1634+`; `server.ts:2584+`; `server.ts:2640+`  
   **Trigger:** An authenticated/modified client directly requests a Notion capability.  
   **Observed:** The server issues the token based entirely on authenticated client-supplied `worldId`, `messageText`, and `allowedTools`. Nothing independently proves that the human checked the UI consent control. The same client Raen considered compromised can mint the replacement capability itself. Worse, Notion tool execution uses the server-global `NOTION_API_KEY`.  
   **Why boundary failed:** client boolean was replaced with a server nonce, but the **authorization event still originates from the same untrusted client**. The trust boundary moved; it was not established.  
   **Smallest containment target:** consent issuance needs an independent trusted user-presence/authorization gate. And the Notion credential must be bound to the authorized user/tenant or explicitly restricted to the Sovereign account.

2. **CRITICAL in a multi-user deployment — global Notion authority crosses Firebase users.**  
   **Path:** `src/App.tsx:2334–2363`, `1180–1228`; `server.ts:1634–1640`, `2584–2655`  
   **Trigger:** Another verified Google-authenticated user signs in. The client automatically creates that user a world. The user now satisfies `requireOwnedWorld` for that world.  
   **Observed:** They can reach Notion operations backed by the same server-level `NOTION_API_KEY`; there is no Court-member/Sovereign UID allowlist or per-user Notion credential binding in source.  
   **Why boundary failed:** “owns a Firestore world” has accidentally become “may use the application's private external integration.” Those are different authorities.  
   **Smallest containment target:** bind the server Notion integration to an explicit principal/ACL. World ownership alone cannot grant it.

3. **HIGH — provenance is still client-forgeable and mutable. Findings #4/#5 are only partially contained.**  
   **Path:** `firestore.rules:44–52`, `65–97`, `151–181`

   **Smallest containment target:** clients must never be able to mint `verified_source` or upgrade provenance. Promotion needs a separate trusted transition/receipt; origin/evidence class should be immutable except through that gate.

4. **HIGH — Saren runtime continuity fails open on a bad handoff.**
